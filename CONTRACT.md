# Contract - cavalry

This contract is the executable spec for cavalry. Every obligation below is stated so it can fail. The full contract is the first build act of this repo and it extends the stub obligations written here.

## Stub obligations

CV-S1. Every recorded rescue carries who intervened, what they did, and which run it touched, and a record missing any of those fields is rejected rather than stored incomplete.

CV-S2. Every rescue is classified into a named class, and a record that cannot be classified is held in an explicit unclassified state that reports itself rather than passing silently.

CV-S3. Every class with at least one recorded rescue carries a drafted hook or rule meant to retire that class, and a class with rescues and no draft is a defect the tests must catch.

CV-S4. Cavalry records human rescues only, and an automatic rescue performed by prod is never written into the cavalry record as a human rescue.

CV-S5. Every fixture and example in this repo is synthetic and built for this repo, and no real trace or session data appears anywhere in the tree.

## Round 1 obligations

Round 1 records the rescues only a human could make. It builds no model calls, it performs no rescue, it grades no rescuer, and it reimplements no automatic ladder from prod. The decision model material in ROADMAP.md is advisory design for later rounds and creates no Round 1 obligation.

CV-1. Every capture input is one JSON object carrying the fields id and run_ref and rescued_role and rescuer_role and rescuer_kind and stalled and human_action and occurred_at and outcome, plus an optional field named corrects, and no other field. The field stalled states what stalled, human_action states what the human did that the automatic ladder could not do, occurred_at states when the rescue happened as supplied by the capturer, outcome states what happened after the rescue, and run_ref names the run the rescue touched.

CV-2. The fields rescued_role and rescuer_role are role labels and never real names. A role label is one token made of a leading lowercase letter followed by lowercase letters or digits or hyphens, and a record whose role field is not a role label in this shape is refused with that field named.

CV-3. Cavalry records human rescues only. The field rescuer_kind must carry the value human, and a record carrying any other value is refused with rescuer_kind named and is never written into the cavalry record as a human rescue.

CV-4. The capture flow is the capture subcommand of the dependency free package cavalry run as python -m cavalry. Capture reads one record from a JSON argument file, validates it, classifies it, and appends exactly one line holding that record as JSON with sorted keys to the end of a records file held in JSON Lines form. A stored record carries every capture field plus a field named rescue_class added by the tooling.

CV-5. Capture validates a record on the way in. A record missing a required field, or carrying a required field with an empty value, is refused with the missing field named in the error and nothing is written. A record carrying an unknown field is refused with that field named and nothing is written. A record whose id is already present in the records file is refused with id named and nothing is written.

CV-6. Every record is classified into a rescue class from the versioned class list held in the repo at cavalry/classes.json. That file carries a version field and one entry per class, and each entry carries a class id and a keyword list and a drafted proposal text. Classification is deterministic and matches the lowercased combined text of stalled and human_action against the keyword lists in list order, and the first matching class wins.

CV-7. A record that matches no class in the versioned list is stored with rescue_class set to the explicit value unclassified. An unclassified record is never forced into a named class, and the list and propose outputs report unclassified records under that name rather than passing over them silently.

CV-8. A record once written is never edited by the tooling. Capture only ever appends to a records file and never rewrites or deletes an existing line. A correction lands as a new record whose corrects field carries the id of the record it corrects, and a correction whose corrects value names no record already present in the records file is refused with corrects named and nothing is written.

CV-9. The list subcommand prints one line per record in file order, and each printed line carries the record id and its rescue_class and its run_ref and its occurred_at and its outcome, so every record reports its class including the unclassified state.

CV-10. The propose subcommand prints one drafted hook or rule proposal for each distinct class present in a records file, in the order of the versioned class list with unclassified last when present. Each printed proposal names its class and carries the word proposal and states plainly that it is a proposal only. A proposal is never applied anywhere by the tooling, and no proposal output edits any other file or repo.

CV-11. Every output of the tooling is deterministic for a given input. No output uses a wall clock, and every timestamp printed comes from the occurred_at field of the record itself as supplied by the capturer. Repeating a command on an unchanged records file produces byte identical output.

CV-12. Every record, fixture, and example used by Round 1 is synthetic and written for this repo. No real name, real trace, real session data, or real operational detail appears in any record, test, or example in the tree.

CV-13. The examples directory holds a synthetic records file with at least three records spanning at least two named classes plus at least one unclassified record, and a committed proposals file holding the output of the propose subcommand run on that records file. The proposals file regenerates byte for byte with the command python3 -m cavalry propose examples/records.jsonl run from the repo root with its output written to examples/proposals.txt.

## Round 1 amendments

The amendments below tighten Round 1 behaviour after the red team audit and the two axis review of the Round 1 build. Each amendment states the behaviour it changes or adds and leaves the earlier text standing, so the record shows both the original obligation and the tightened one.

CV-14. Capture appends safely to a records file whose last line carries no trailing newline. When the records file is not empty and its last byte is not a newline, capture writes the missing newline first and then writes the new record line, so the bytes already stored stay an untouched prefix of the file and every stored record stays readable by the tooling.

CV-15. Every line read from a records file must hold one stored record. A line that parses as JSON but is not an object, or an object missing any field of the stored field set, or an object carrying a field outside that set, or a field whose value is not text, is refused by every subcommand with the records error naming the defect, and in that case no subcommand writes anything and none leaks a traceback or a bare internal error. The stored field set is every capture field plus rescue_class.

CV-16. The propose subcommand never passes over a stored class in silence. A stored record whose rescue_class names no class in the versioned class list and is not the unclassified value makes propose refuse with the records error naming that class.

CV-17. Keyword matching is whole word matching and ignores case on both sides. A keyword matches only where it appears in the combined text as a whole word or as a whole word with a trailing s, and a longer word that merely contains a keyword inside it never matches. Keywords are lowercased when the class list loads and the combined record text is lowercased before matching. The keyword lists in cavalry/classes.json spell out each word form they intend to catch in place of the stems the first version relied on, and the class list version rises to 2 for this change.

CV-18. A role label must match its shape over the whole value. A role field carrying any extra character around the label, including a trailing newline, is refused with that field named.

CV-19. The class list is validated when it loads. The file must carry its version and its unclassified proposal text, and every entry must carry a class id and a non empty keyword list and a non empty proposal text, and any defect in the file is refused with the records error naming the entry and the field rather than leaking a bare key error.

CV-20. The proposal text for the unclassified state lives in cavalry/classes.json alongside the named classes, and the tooling reads it from that file, so no proposal text is hardcoded in the package.

CV-21. The occurred_at field must carry a timestamp in the shape the examples carry, namely a four digit year and a two digit month and a two digit day joined by the letter T to a two digit hour and a two digit minute and a two digit second, with an optional trailing Z, and a record carrying any other shape is refused with occurred_at named.

CV-22. No field value in a capture input may carry a newline character or a carriage return character, and a record carrying one is refused with that field named, so a stored value can never shape the lines the list subcommand prints.

## Round 2 obligations

Round 2 builds the decision model seam that Round 1 deferred. The Round 1 statement that the decision model material in ROADMAP.md creates no Round 1 obligation stands for Round 1, and the obligations below lift that deferral for this round and no other. The seam is built and tested offline against recorded fixtures, and no obligation below makes a live model call. Cavalry still records human rescues only, it still performs no rescue and grades no rescuer, the record a human made still stands exactly as written, and a drafted hook or rule still leaves this repo only as a proposal.

CV-23. Judgment enters the record pipeline at exactly two points and nowhere else. Classification review asks which rescue class a record belongs to and answers with a choice over the class identifiers in the versioned class list plus one further label named new-class that names a class not yet on the books. Record quality asks how classifiable a record is and answers with a score. No judgment performs a rescue, edits a record, rejects a record, or replaces the deterministic classification, and no judgment is asked about anything else.

CV-24. A classification request is a JSON object carrying the record id under record_id and the record text under stalled and human_action and the offered class identifiers under classes in versioned list order. A quality request is a JSON object carrying the record id under record_id and the record text under stalled and human_action and the outcome text under outcome. A request is built from the record and the class list and from nothing else, and two requests are the same request only when the point and every field match exactly.

CV-25. A judgment is recorded as a fixture file holding one JSON object carrying exactly the fields judgment_point and request and response and synthetic, and the synthetic field carries the value true. A choice response carries exactly the fields kind and choice and confidence and probabilities, its probabilities carry one number for every label the point offers and those numbers add up to 1, and its choice names one of those labels. A score response carries exactly the fields kind and score and confidence. An abstention response carries exactly the field kind with the value abstention. Every score and every confidence and every probability is a number between 0 and 1, and the labels a classification point offers are the class identifiers in the request plus the new-class label, and the labels a quality point offers are none because quality answers with a score.

CV-26. The fixture player loads every JSON file in one fixtures directory and validates each recorded pair as it loads, and a pair that breaks the recorded shape refuses the whole directory with an error naming the file and the defect. Two fixtures recording the same point and the same request are refused at load with the later file named. The player answers a request only from a recorded fixture whose point and request match exactly, and it returns no answer where nothing matches, and returning no answer is the abstention the pipeline understands. The player reads files from its directory and nothing else, and it makes no network call and reads no clock.

CV-27. A judgment answer is trusted only when it is well formed for its point under the recorded shape and its confidence reaches 0.6. An answer below that confidence and an abstention and an answer outside the recorded shape for its point, including an answer of the wrong kind for the point, and the absence of a judgment source all count as no judgment at all. Before any answer is trusted, the capture flow checks the answer against the recorded shape for its point whatever source produced it, and an answer that fails that check counts as no judgment and is never recorded and never makes the capture fail.

CV-28. When capture runs with a judgment source and the classification answer is trusted, the stored record carries a field named proposed_class holding the proposed class identifier or the new-class label, and a field named review_state holding the value proposed. The rescue_class on the record is computed by the deterministic classification exactly as Round 1 computed it and is never replaced by a proposal. Where the deterministic classification already placed the record in a named class, the proposal still attaches as a second opinion with its own state, and the deterministic class and the proposed class stand side by side on the record until a confirmation settles the record into the class history.

CV-29. When no classification answer is trusted, for any of the reasons in CV-27, the stored record carries review_state holding the value unreviewed and carries no proposed_class field, and that is the state records waited in before the seam existed. Every record the seam writes carries its review_state. A record written before the seam carries no review_state field, and wherever the tooling reads a review state such a record reads as unreviewed. A quality answer never changes the review state of a record.

CV-30. When capture runs with a judgment source and the quality answer is trusted and its score falls below 0.5, the stored record carries a field named quality_flag holding the value below-bar. A trusted quality score at or above 0.5 records no flag. No quality answer ever edits a record or refuses a record or changes its class or its review state, and the flag is the whole of what the score does, and it marks the record for a follow up conversation with the rescuer.

CV-31. The stored field set gains four optional fields named review_state and proposed_class and quality_flag and confirmed_class, and each holds text when present. A stored record whose review_state holds proposed must carry proposed_class, and a stored record whose review_state holds confirmed must carry confirmed_class, and a stored record carrying a review_state outside unreviewed and proposed and confirmed is refused under the records error discipline of CV-15. Every Round 1 stored field keeps its name and its meaning, and a records file written under Round 1 still reads and lists and proposes exactly as it did under Round 1.

CV-32. A confirmation is a recorded act that names one record and one class, and the human who confirms is the only actor who can settle a proposal into the class history. The confirm subcommand reads one JSON object carrying exactly the fields record and class from an argument file. It refuses an object carrying any other field or missing either field, and it refuses a record id that names no record in the records file, and it refuses a record that carries no proposal under review, and it refuses a record that already stands confirmed, and it refuses a class that names no class in the versioned class list and is not the unclassified value. The new-class label names no class on the books and can never be confirmed. Every refusal names the defect and writes nothing.

CV-33. A successful confirmation appends exactly one new record to the records file and edits no existing line, under the same safe append discipline as capture. The appended record copies the named record fields exactly, and it carries corrects naming the record it confirms, and it carries an id made of the named record id plus the suffix --confirmed, and it carries review_state holding the value confirmed, and it carries confirmed_class holding the confirmed class, and it carries the proposed_class and the quality_flag of the named record when the named record carries them, and its rescue_class is the deterministic classification of the copied text. The class history counts a confirmed record under its confirmed_class in place of the record it confirms, and an unconfirmed proposal counts nowhere in the class history, and the propose subcommand reports the counted classes under this rule, and a records file holding no confirmation proposes exactly as Round 1 proposed.

CV-34. The capture subcommand accepts an optional fixtures flag naming a fixtures directory, and with the flag the capture runs with the fixture player for that directory as its judgment source, and a fixtures directory that cannot be loaded is refused with the error naming the defect and nothing is written, and without the flag capture behaves exactly as Round 1 behaved. The confirm subcommand takes a confirmation file and a records file in the same argument shape as capture, and it prints one line naming the record confirmed and the class it was confirmed into. Every output of the seam is deterministic for a given input, and no output uses a wall clock.

## Round 3 amendment

Round 3 hardens the validation of the decision model seam and changes no behaviour for any well formed fixture or any well formed answer. The amendment below states the hardened discipline exactly, and it leaves every Round 2 obligation standing.

CV-35. The validation of a recorded fixture and of an answer from any source follows one hardened discipline. The fixture envelope carries exactly the fields judgment_point and request and response and synthetic, and a fixture carrying any other top level field is refused at load with that field named. A response carries exactly the fields its kind carries under CV-25, and a response carrying any other field is refused at load and counts as no judgment from any other source, with the extra field named in the refusal. A response whose kind is not a string is a malformed answer, and it is refused at load and counted as no judgment by the answer check, and neither path raises on it. A value that cannot be converted to a finite float is not a number for the checks of this seam, so a score or a confidence or a probability carrying such a value is refused at load and counts as no judgment from any other source, and the trust check returns false for an answer whose confidence carries such a value rather than raising on it or accepting it, and an infinite confidence is never trusted. Where a refusal names an extra field and the fixture or the response carries extra fields of mixed types, the extra fields are ordered by their printed form, so the refusal names one and raises no comparison error, on the load path and on the answer check path alike. The probabilities of a choice response add up to 1 within a tolerance of one thousandth, and the sum is computed in binary floating point in label order, and the computed sum is what decides at the edge of the tolerance. No well formed fixture and no well formed answer changes its treatment under this amendment.

## Round 4 amendment

Round 4 states the rules that govern the records store and the versioned class list as the list changes over time. The list already changed once in Round 1, and the store is append only, so records written under an earlier list stand beside records written under the list in force. The readings below were probed against the Round 3 code before this amendment was written, and every clause held. The round's review then exposed three corrupt shapes the stated rules cannot govern, and the last sentences of the amendment refuse those shapes from this round rather than leaving the rules overclaimed. The amendment leaves every earlier obligation standing.

CV-36. The records store is history and the class list is current data, and the two meet under fixed rules. A stored record is read as recorded, and reading and listing a records file never test a recorded class against the class list in force, so a record classified under an earlier list still reads and lists byte as stored after the list moves on. The proposals document counts a confirmed record under its confirmed class and every other record under its recorded rescue class, and a record a confirmation supersedes is counted only through the record that confirms it, and where a counted class stands in neither the class list in force nor the unclassified value the document is refused whole with an error that reads records hold an unknown rescue_class and then names the first such class in sorted order, whichever counted field carried it, and no proposal is printed. A proposed class is never a counted class, so a record whose only stale name sits in its proposed class counts under its rescue class and its proposal prints exactly as it prints for a record carrying no stale name. A confirmation is judged against the class list in force exactly as CV-32 states, so a record proposed under a class the list has since retired still confirms into a class on the current books, and the appended record carries the proposed class forward as recorded while its rescue class is the deterministic classification of the copied text under the list in force. The class list is accepted on its shape alone, and its version field must be present and must carry a whole number and is carried for the humans who keep the list, and the tooling never acts on its value, so a well formed list whose version carries any other whole number loads and classifies and proposes exactly as the list it replaces. The counting above keys on a record's id, and a records file carrying two records under one id is refused at read with an error naming the line and the id, so no record can hide behind another record's id and no count or confirmation depends on the order of the lines. The class list in force names each of its classes once and names no class with the unclassified value, and a list breaking either rule is refused at load, because a class named unclassified would render as the unclassified value everywhere the two must stand apart.

## Round 5 obligations

Round 5 ports cavalry to Rust under the program wide ruling that these repos are Rust libraries. The Python implementation of Rounds 1 to 4 is the behavioral spec for the port and its test corpus is the parity corpus. The port reproduces the contracted behavior exactly, documents and records and exit behavior included, and the Python is removed inside the same slice once the parity is proven by differential. Cavalry still records the rescues only a human could make, it still performs no rescue, and the port reimplements no rung of prod's ladder and no switch of deadman's.

CV-37. The implementation of the tool is a Rust crate named cavalry. The crate carries a library target that holds the contracted behavior in modules mirroring the modules of the rounds before it, and a binary target named cavalry carries the command line with the capture and list and propose and confirm subcommands, the same arguments, the same exit codes, and the one error line discipline the command line has always carried. The crate depends on clap in its derive form for the command line, on thiserror for the library error types, on anyhow inside the binary entry point and nowhere else, and on sha2 for the digest the setup test checks.

CV-38. The Rust implementation reproduces the behavior CV-1 to CV-36 state, exactly and without reinterpretation. Every behavior the Python test corpus pinned is pinned by a Rust test asserting the same behavior, and no earlier obligation is weakened, dropped, or read more narrowly because the language changed.

CV-39. Every document the tool emits is byte identical to the document the Python implementation emits for the same input. The identity covers the stored record lines with their sorted keys and their string escaping, the list and propose documents, the capture and confirm lines, the error lines of the tool's own refusals with the Python reader's defect text standing inside them where the rounds before it placed it, and the exit codes. A difference in any byte is a defect in the port and never a new behavior.

CV-40. Numbers and strings print as Python prints them. An integer prints as an integer and keeps every digit at any length. A float prints in the shortest decimal form that round trips to the same value, with the exponent form used exactly where the Python repr uses it and withheld exactly where the Python repr withholds it. A string written into a JSON document is escaped as Python json escapes it with ensure_ascii in force, so a non-ASCII character appears as a unicode escape sequence and never as raw UTF-8 bytes inside an emitted JSON document. A field name a refusal names renders as the Python repr of the name renders it, and a set of extra fields is ordered by that printed form when a refusal names one of them, as CV-35 states.

CV-41. Where a key or a comparison is built from JSON text, the text is the Python dumps form of the value with sorted keys and the default separators, so every matching decision the fixture player makes lands on the same side it landed on before the port.

CV-42. The depth ceilings and the digit limit of the Python tool stand in the port at the depths the probes measured. The JSON reader carries a document whose deepest container path is 9994 containers and refuses a document past that path. The fixture player's request key is built from a document whose root names the point and the request, and that key building carries a key document whose deepest container path is 9991 and refuses a fixture whose key document path passes it. A JSON integer literal of more than 4300 digits fails to convert. Each of those three failures is one the Python tool never catches, escaping there as a recursion error or a bare value error at exit status 1, and the port answers each at the same depth and the same status with one error line of its own naming the surface as nested too deeply or the integer as too long. The response copy inside the fixture player's judge step copies a response through a dumps and loads round trip exactly as the Python player does, and no ceiling of this obligation is stated for it, because a response that survives the load validation of CV-25 and CV-35 stands at most three containers deep and the copy never nears either ceiling.

CV-43. A standard output that cannot take the bytes divides by the size of the printed output, because the Python tool holds that output in a buffer of 8192 bytes on its way out. A failure under an output of 8192 bytes or more surfaces while the output is being written, and cavalry's command line catches that failure as a system error and answers it with its own error line at exit status 2, the line carrying the platform error text with its error number and no file name. A failure under a smaller output surfaces only when the buffer is flushed as the tool exits, and the Python tool reports it as an exception ignored at shutdown and exits with status 120 and no traceback. The port answers both shapes at the same status, the during write shape in the same error line form the Python tool gives it and the flush shape in its own one error line in place of the shutdown report. A record a capture appends before its printed line fails stands appended in both shapes, exactly as it stands under the Python tool.

CV-44. The Python implementation is removed inside this same slice, and it is removed only after the byte parity CV-39 demands is proven by a differential that runs both implementations over the committed examples and the committed fixture pairs, over the four subcommands in sequence on one records file, and over a generated corpus of hostile records files and hostile class lists and hostile fixture directories, comparing standard output, standard error, exit codes, and every emitted file byte for byte. After the removal the repo builds and tests with cargo alone, and the CI backstop step runs the cargo test suite.

CV-45. The setup invariants stand re-expressed as Rust tests. The canonical block of AGENTS.md still hashes to the digest the setup pins, the text files of the tree still carry no em dash and no en dash, and the README still reports the closed round count in the pinned form with the count the round record states, the pin reading the count phrase over the whole README exactly as the Python setup test read it.

CV-46. The command line surface keeps its functional outcomes and changes its presentation only where this obligation states. Help text and malformed invocation error text follow clap in its own forms. The subcommands and their arguments are the same, misuse still exits with status 2, help still exits with status 0, and unambiguous long flag abbreviations still execute at the top level and inside a subcommand. A help token fires where the Python parser's scan fires it, ahead of extra tokens the scan already collected and never in a value position, and a help token carrying an explicit value is refused. A word the subcommand slot cannot take ends the scan at once, so a help token after it never fires, while an unknown option token is only collected and a help token after it still fires. One separator token is consumed wherever it stands, before or between or after the positional arguments, and every token after it is a positional value, so a second separator is itself a value. A value that looks like a negative number under the Python matcher's two anchored patterns over the Unicode decimal digits is taken as a value, and a value carrying a space is taken as a value whatever its prefix. A fixtures flag carrying an empty value reads exactly as no fixtures flag at all, and a fixtures flag given twice takes its last value. Arguments arrive as OS strings and never through a panicking UTF-8 conversion, and a path argument is rendered in the tool's error lines as Python renders it, the path library's folded form for the paths the records discipline names and the surrogate escape text standing for every byte Python cannot decode. A system error the command line catches prints with the platform error text and its error number and the path in the path library's form, exactly where the Python tool printed it.

CV-47. The versioned class list stays at cavalry/classes.json, the path CV-6 and CV-20 name, as declarative product data. The binary carries the shipped list inside itself at build time, and the library reads the shipped list and a list supplied from any other path through one and the same loading and validation path, so the readings CV-19 and CV-36 state hold identically for both.

Probe correction to CV-37, recorded before the build and governing where the two disagree. The dependency sentence of CV-37 as first written followed the fleet stack ruling in naming serde and serde_json by implication as the JSON foundation. A probe run against both JSON readers before the build showed that the serde_json reader cannot carry the reading behavior the earlier rounds pinned. It reads an integer with thirty digits as a float and loses the integer, and it refuses the NaN and Infinity constants and a float literal too large for its range where the Python reader accepts all of them and reads the large float as infinity, and it reports none of the Python reader's defect text that CV-39 places inside the tool's error lines. Byte parity under CV-39 is impossible on that reader, so the crate carries its own JSON value model and its own reader and writer inside its own module, and serde and serde_json are not dependencies of this crate. Every other word of CV-37 stands.

Probe correction to CV-39, recorded before the build and governing where the two disagree. The byte identity CV-39 demands carries three exception families the port cannot remove. The first is the lone surrogate reading. A JSON string carrying an unpaired surrogate escape is read by the Python reader as the lone code unit and written back as that same escape in every emitted document, and a Rust string cannot hold a lone surrogate, so the port reads such an escape as the replacement character U+FFFD and writes that character in its escaped form where the Python document carries the surrogate escape. Two texts that differ only in unpaired surrogate escapes are the same text to the port, because a Rust string holds the replacement character where the Python reader holds the surrogate itself, while the Python reader keeps such texts distinct. The same forced reading reaches the command line, where text whose bytes are not valid UTF-8 reaches the Python parser through its surrogate escape decoding as lone surrogate code units and is written in escaped form, and the port reads the same bytes as the replacement character. The second family is the failures the Python tool never catches, stated in CV-42 together with a file whose bytes are not valid UTF-8 where a fixture file's own reading would refuse it in the tool's words. An input file or a records file that is not valid UTF-8 fails in the Python tool as an uncaught decode error at exit status 1, and the port answers it at the same status with one error line of its own. The third family is the standard output family of CV-43, whose two shapes the port answers at the same statuses in its own line where the Python tool prints a shutdown report. Every other byte stands as CV-39 states.
